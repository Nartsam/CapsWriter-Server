## 已知问题 / 怪现象

- **识别结果有随机性**（2026-09-28）：Qwen3 解码温度 0.4（采样），同一段音频多次识别可能在标点或个别字上不同。
- **对齐模型的 LLM 走 CPU**（2026-10-01 更新）：`ForceAlignerGGUFArgs.llm_use_gpu = False`（上游默认），16 秒音频的文件任务在 Windows 上首次约 8.5s（含加载对齐模型），对齐模型还没被释放时约 4.6s；麦克风任务不受影响。
- **默认日志级别 WARNING**（2026-09-28）：llama.cpp 的 Vulkan 设备、ONNX 实际后端等信息是 INFO 级别，排查性能问题时先把 `log_level` 改为 `'INFO'`。
- **同目录多实例共享日志与状态文件**（2026-09-28）：在另一个端口起测试实例时，`logs/server_latest.log` 与 `logs/server_status.json` 会和正在使用的实例混写。
- **识别子进程中途退出后服务端不会发现**（2026-10-01）：`process_manager` 只在加载模型期间检查子进程是否存活；之后子进程若退出，主进程照常接受连接，客户端会一直等不到结果，日志里也没有记录。曾在本机同时运行三个实例、系统提交内存将近耗尽时遇到过一次，单实例压力测试（120 次请求）没有出现。
- **推理内核里未用到的入口**（2026-09-28）：`inference/asr.py` 的 `transcribe()` / `asr()` 是上游的整文件转录接口，服务端不走这条路，它依赖的 `soundfile` 已不在运行时里。
- **exe 输出重定向到管道时是 GBK 编码**（2026-09-28）：这是控制台代码页，日志文件是 UTF-8。

## 仍然有效的决策

- **模型不进 git**（2026-09-28）：单个 gguf 就有 1.47GB，只能走 Git LFS，而 GitHub 免费 LFS 额度有限，所以改从上游 Release 下载并做 SHA-256 校验。本地文件与上游压缩包逐文件 CRC32 一致。风险：上游删除或重新上传这些压缩包时，需要换 `ModelDownload.base_url`（例如传到自己仓库的 Release），并更新 `model_download.py` 清单里的 SHA-256。
- **编码器默认走 DML，不移植上游 v2.6 的「GPU 预加速」**（2026-10-01）：本机（GTX 1080 Ti，双显示器）DML 比 CPU 快 1.5~3 倍（数据见 [显卡加速.md](显卡加速.md)）。预加速是在录音开始时以管理员权限执行 `nvidia-smi -lmc`；本机空闲时显存频率一直是最高值，空闲 60 秒后再识别也没有额外延迟，移植过来不起作用，还要求以管理员身份运行服务端。换到会降频的机器上，先按显卡加速.md 手动锁频。
