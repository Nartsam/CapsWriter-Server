# 显卡加速

Qwen3-ASR 由两部分组成，分别由不同的推理库运行：

| 组件 | 模型文件 | 推理库 | Windows 可选后端 | Linux 可选后端 | 配置项 |
|---|---|---|---|---|---|
| 音频编码器 | `*.onnx` | ONNX Runtime | CPU / DML（DirectML） | CPU / CUDA | `onnx_provider` |
| LLM 解码器 | `*.gguf` | llama.cpp | CPU / Vulkan | CPU / Vulkan | `llm_use_gpu` |

配置在 [`config_server.py`](../config_server.py) 的 `Qwen3ASRGGUFArgs`（识别）和 `ForceAlignerGGUFArgs`（对齐）里。当前默认值：

| | Windows | Linux |
|---|---|---|
| `onnx_provider` | `DML` | `CUDA` |
| `Qwen3ASRGGUFArgs.llm_use_gpu` | `True`（Vulkan） | `True`（Vulkan） |
| `ForceAlignerGGUFArgs.llm_use_gpu` | `False` | `False` |

为什么两个平台的 `onnx_provider` 默认值不同：Windows 的 `internal/` 里打包的是 **onnxruntime-directml**，没有 CUDA；Linux 环境装的是 **onnxruntime-gpu**，没有 DirectML。请求的后端不可用时会回退 CPU，日志里有 `ONNX 推理后端 … 不可用，已回退到 …` 的警告；正常时日志（INFO 级别）显示 `ONNX 推理后端：CUDAExecutionProvider` 之类。

启动时也可以用环境变量 `CAPSWRITER_ONNX_PROVIDER=CPU|CUDA|DML` 临时覆盖（见 [PROJECT_INDEX.md](../PROJECT_INDEX.md) 的“启动参数”）。

## ONNX 编码器

- **DML（Windows）**：每次输入形状变化 DirectML 都会重新编译着色器，所以会把短音频统一填充到 `dml_pad_to` 秒（默认 30）使形状固定；更长的音频不填充，但实测重新编译的开销很小。上游作者实测部分 AMD 显卡开 DML 反而更慢，所以上游默认 CPU；本仓库默认 DML，换到其他显卡上如果变慢，把 `_DEFAULT_ONNX_PROVIDER` 改回 `CPU`，或启动时设置 `CAPSWRITER_ONNX_PROVIDER=CPU` 对比。
- **CPU 与 DML 实测对比**（GTX 1080 Ti，从发送完成到收到结果，取中位数）：

  | 音频时长 | 编码器 CPU | 编码器 DML |
  |---|---|---|
  | 3 秒 | 0.38s | 0.26s |
  | 6 秒 | 0.64s | 0.44s |
  | 16 秒 | 1.43s | 0.72s |
  | 31 秒 | 3.69s | 1.44s |
  | 64 秒 | 8.48s | 2.69s |
  | 16 秒文件转录（含对齐） | 6.5s | 4.6s |

  两者的识别结果一致；DML 多占约 0.8GB 显存。机器上其他程序占用显卡时，数值会有波动。
- **CUDA（Linux）**：需要 CUDA 12 + cuDNN 9 运行库。`setup_linux.sh` 默认以固定版本的 `nvidia-*` pip 包装进环境（见 `requirements-linux.txt`），只依赖显卡驱动；`start_server.sh` 会把这些库加入 `LD_LIBRARY_PATH`。cuDNN 的版本是固定的，换显卡前先看 `requirements-linux.txt` 里的说明。

## llama.cpp 解码器

- 打包的 llama.cpp 是 **Vulkan** 版（Windows 与 Linux 都是 b7798），显卡驱动需提供 Vulkan 支持。Linux 上需要 NVIDIA 驱动附带的 Vulkan ICD（`/usr/share/vulkan/icd.d/nvidia_icd.json`），Vulkan 加载器 `libvulkan.so.1` 已随仓库提供。
- 找不到 Vulkan 设备时 llama.cpp 会退回 CPU，识别延迟会明显变长；日志里 `ggml_vulkan: Found N Vulkan devices` 可确认是否用上了显卡（需要 `log_level = 'INFO'`）。
- 部分 Intel 集显在 GPU 解码时可能精度溢出导致乱码，只能把 `llm_use_gpu` 改为 `False`。
- 多卡机器用 `--gpu N` 指定只用第 N 张卡（同时设置 `GGML_VK_VISIBLE_DEVICES` 与 `CUDA_VISIBLE_DEVICES`）。

## 显存降频（NVIDIA，可选优化）

NVIDIA 显卡空闲几秒后可能降低显存频率，上游作者实测 RTX5050 上短句延迟因此从约 100ms 升到约 300ms。先确认自己的显卡会不会降频：不做识别时运行下面的命令看几秒，`clocks.mem` 一直是最高频率（与 `clocks.max.mem` 相同）就不需要处理。接了多台显示器的机器常常一直保持最高显存频率。

```bash
nvidia-smi --query-gpu=pstate,clocks.mem,clocks.max.mem --format=csv -l 1
```

确实会降频时，用管理员权限锁定显存频率（上游示例的数值是 9000，可参考上面查到的最高频率）：

```bash
nvidia-smi -lmc 9000
```

每次开机后执行一次即可（Windows 可用任务计划程序在启动时以最高权限运行）。

## 资源占用参考

- 显存：Qwen3-ASR 约 2.5GB（编码器走 CPU 时约 1.7GB）；对齐模型只在文件转录时按需加载，另占约 0.5GB；编码器走 CPU 时闲置 `aligner_idle_timeout` 秒（默认 10）后自动释放，走 DML（Windows 默认）时加载后常驻，因为释放它的 DML 会话会让识别子进程崩溃（见 `core/server/engines/manager.py`）。
- 上游作者的性能参考（20 秒音频）：CPU（U9-285H）约 4.0s，GPU（RTX5050）约 1.0s。

## 耗时分布与已测试过的调整（2026-10，llama.cpp b7798）

GTX 1080 Ti + i7-8700K，编码器 DML、解码 Vulkan，在识别进程内计时（不含网络传输）：

| 语音时长 | 音频编码 | LLM 预填充 + 生成 | 合计 |
|---|---|---|---|
| 3 秒 | 0.08s | 0.13s | 0.22s |
| 16 秒 | 0.11s | 0.54s | 0.66s |
| 64 秒 | 0.41s | 2.08s | 2.50s |

- 耗时主要在 LLM 逐个 token 生成：约 8.5ms/token，中文大约每秒语音 2.3 个 token。采样每个 token 约 0.4ms；llama.cpp 自带的 `llama-bench`（纯 C++）同样是 117 token/s，Python 层没有可省的开销。
- 瓶颈在显卡：llama.cpp 在 Pascal 上不启用 CUDA Graphs，每个 token 要逐个启动几百个内核，有效显存带宽只用到约 170GB/s。

下面这些调整都在同一台机器上测过，没有采用。换显卡或升级 llama.cpp 之前不必重测：

| 调整 | 结果 | 结论 |
|---|---|---|
| 关闭 flash attention | 差别在 ±5% 以内，长音频略慢 | 保持开启 |
| `GGML_VK_DISABLE_F16=1` | 无变化 | 不需要 |
| llama.cpp `n_ubatch` 512 → 1024 | 只在超过 512 个 token（约 38 秒以上）时有用，64 秒快 0.1s | 不值得改 |
| `dml_pad_to` 改为 20 / 10 / 0（不填充） | 编码器后端从 0.07s 变慢到 0.14~0.22s | 保持 30 |
| 编码器前端一次批处理所有块 | 前端模型的 batch 维固定为 1，做不到；前端本身只占 0.02~0.08s | 不做 |
| 贪心采样代替温度采样 | 每个 token 快不到 0.1ms | 与速度无关 |
| llama.cpp 改用 CUDA 后端（同为 b7798） | 快 9%~27%，主要是预填充变快；生成速度不变（8.7 vs 8.2ms/token） | `ggml-cuda.dll` 445MB，另需 CUDA 运行库约 400MB，超过 GitHub 单文件 100MB 上限。换到 Ampere 及更新的显卡（能用 CUDA Graphs）时再评估 |
| LLM 换 q4_k 量化 | 快 9%~12% | 可能损失准确率，要用上游的 q4_k 文件在真实录音上对比后再定（测试用的是从 q5_k 二次量化的文件） |
| LLM 换 q4_0 量化 | 快约 22% | 64 秒长音频漏掉一大段内容，排除 |

测试方法：把 `start_server.exe`、`config_server.py`、`core/` 复制到 `logs/` 下的测试目录，`internal/` 与 `models/` 用目录联接（`mklink /J`），再把副本的 `core/server/app.py` 换成计时脚本。正式代码和正在运行的服务端都不受影响。清理时**先用 `rmdir` 拆掉联接**再删目录，直接 `rm -rf` 会删到联接指向的真实目录。
